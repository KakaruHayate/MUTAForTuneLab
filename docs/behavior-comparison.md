# 行为比对：MUTA 本体 vs MUTAForTuneLab

本次重新从零做行为比对，不复用历史结论。基准只有三样东西：MUTA 自己导出的音频、
TuneLab 工程文件、以及本次重新构建的插件（带诊断输出）。文中的每个数字都能用 `re/` 下的
脚本重跑。

**哪些是"不一致"，哪些是"有意的改进"**：本文只登记实测到的行为差异；声码器、日文链路、
限幅、电平对齐这类已知的有意改动不算在内。每条差异后面都标了"不一致"或"我们不同但有意"。

## 1. 连音 / 转音

### 1.1 MUTA 的实测行为

**音高过渡（转音）**：对 71 个"音高不同、中间没有休止"的音符边界测 F0 轨迹（10%→90% 的
跨越时间）：

| 量 | MUTA |
|---|---|
| 滑音时长中位 | **70 ms**（四分位 45–90；音符较长、间隔干净的样本 85–110 ms） |
| 起点相对音符边界 | **提前 67 ms**（提前量中位；干净样本 57–72 ms） |
| 终点相对音符边界 | 滞后 23–38 ms |
| 与音程的关系 | 2 半音和 7 半音的滑音时长相近 → **基本不随音程变化** |
| 形状 | 归一化 0.19/0.37/0.58/0.62/0.68/0.74/0.85（10/25/40/50/60/75/90%）：两端慢、中段快，近似 S 形 |

也就是说，MUTA 的转音**跨在音符边界两侧**：边界前 ~60 ms 就开始离开旧音高，边界后 ~30 ms
落到新音高。

**连音符（`-` / `+`）**：用谱通量（200–6000 Hz 正差异，10 ms 帧）衡量"是否重新起音"：

| 边界类型 | MUTA | 插件（当前源码） |
|---|---|---|
| 音符内部（参照） | 0.357 | 0.287 |
| 内容 → 内容 | 0.803 | 0.740 |
| 内容 → `-` | **0.487** | 0.740 |
| 内容 → `+` | **0.461** | 1.381 |

MUTA 在 `-`/`+` 处几乎和音符内部一样平滑（不重新咬字），但音高照样按上表滑过去。

### 1.2 插件当前的实现与差异

- **滑音**（不一致）：`F0Mechanism.Build(..., p5: true)` 的 P5 只在**新音符内部**动作——
  用一条从 `f0[start-1]` 到 `f0[start+b4]` 的直线替换开头，`b4 = min(20% 音符长, 60 帧)`。
  实测滑音中位 40 ms（15–59），起点就在边界上（lead≈0），形状是分段直线（0.26/0.29/0.34/
  0.43/0.43/0.83/0.88）。听感上就是"到拍子上才甩上去"，而 MUTA 是提前起滑、跨拍落点。
- **连音重新起音**（不一致）：`MutaSynthesisSession.Continue()` 保留了 head 的
  `ModelPhones`（标签层仍然把整个音节再唱一遍，为了让"标签音素数=期望音素数"的对齐检查
  通过），只把 `BankInitial` 置空。于是选槽层为连音符**重新选一段韵母录音**，从第一个采样
  就是满幅，和前一音符的尾音之间没有交叉淡化 → 一个阶跃（谱通量 0.74/1.38，比内容→内容
  还高）。
- **MUTA 的做法**：`LabelBuilder.ExpandNotes` 里 `IsDash(phone) → continue`——`-` **不产生
  任何 slot**，head 的韵母 slot 被拉长覆盖两个音符。连音符在标签层是不存在的，所以既不会
  重新咬字，也不会重新选录音。
- **`+` 的语义**（我们不同但有意）：TuneLab 本体只把 `-` 当延音符
  （`INoteExtension.IsEditorContinuationLyric`），`+` 对宿主只是一个普通歌词；"算不算延音"
  是问会话的 `IsContinuation`。插件把 `+` 也当连音——这与 **MUTA 实测一致**（MUTA 在 `+`
  处同样是平滑延续），但与 TuneLab 自身的语义不同。这条要保留，但要在文档里写清楚：`+`
  是插件扩展，宿主单独打开这个工程时不会把它画成延音。

### 1.3 建议

1. **滑音跨边界**：在逐帧 F0 生成之后加一道"过渡"处理——对相邻、相接（或间隔 < 1 帧）且
   音高不同的音符对，把 `[边界-60ms, 边界+30ms]` 这段的目标音高用 smoothstep 从旧音高
   插到新音高，再叠回载波的微形状；时长不随音程变化（实测如此）。
2. **连音不重新起音**：标签层对 `-`/`+` 不产生新 slot（学 MUTA），head 的韵母 slot 覆盖
   连音符的时值；选槽层对连音符不选新韵母，改为延长 head 的那段录音（或与 head 尾部交叉
   淡化）。几何上报 body 继续、不报新的 leading。
3. 对齐检查要允许"连音符不产生音素"这一种情况，否则会误判为失败。

### 1.4 已实现（test6）

- **滑音跨边界**：`F0Mechanism.Build` 的 P5 改成真正的跨边界过渡——从边界前 90 ms
  （`TransitionLeadFrames = 18`）到边界后 30 ms（`TransitionTailFrames = 6`），在
  半音域上做 smoothstep 插值，再除以当前帧所属音符的目标值、乘回载波的微形状，保留
  vibrato/进音。跨边界过渡生效时该音符不再走自己的起音斜坡（否则会先到音高、再掉回
  斜坡，实测是一次"回落"）。
- **连音不重新起音**：判定统一在会话里做（`-` 与 `+` 都是乘客）。标签层不为乘客产生
  槽位（`BuildScore` 跳过并把时值加到链头），bank 层也不为它选槽，链头韵母按
  `note.Frames + 乘客帧数` 拉伸、`MarkVoiced` 覆盖整段；几何的 `FillEnd` 也铺过乘客。
  宿主拿到的 `SynthesizedPhonemes` 里乘客是"零音素"（SDK 允许的三态之一），链头韵母
  时长覆盖整段。日文链路把乘客并入前一个 mora 的时值，Sinsy 只唱一个长母音。
- **验收**（参考工程 280 音符）：谱通量 content→`-` 0.740 → **0.325**（MUTA 0.487），
  content→`+` 1.381 → **0.333**（MUTA 0.461），已无重新咬字；`porta.py` 在 71 个
  边界里测到插件 128 条滑音，中位 **65 ms**（MUTA 70），提前量中位 **77 ms**（MUTA 67）。
- 分块器不会在乘客前断开，所以链头总在同一块内；块首如果仍是孤儿乘客，会退化成内容。

## 2. 句首巨大杂音

### 2.1 现象

在 `re/out/real.wav` 里，短休止后第一个辅音出现之前，有 **16 处** 10–40 ms 的宽带噪声：
RMS 0.29–0.46（正常演唱中位 0.034），单采样峰值 0.999，频谱质心 ~8 kHz，能量集中在
2–24 kHz。听感就是"句首一声爆音"。

出现位置（秒）：21.25、28.33、31.42、32.57、40.53、43.37、59.86、62.09、64.75、120.36、
122.53、125.20、148.78、150.97、153.66、176.55。

### 2.2 证据链

插件自身的日志（本次加的诊断）把"有声但没写过的帧"逐帧打出来，和上面的爆音逐点吻合：

```
unwritten voiced frames: 1 of 1056 at frames [506] (21.252)s
unwritten voiced frames: 3 of 1819 at frames [522,1141,1370] (28.332,31.427,32.572)s
unwritten voiced frames: 2 of 2484 at frames [651,1219] (40.538,43.378)s
```

最小复现（`re/cases/gap.cmd.txt`：`a` / 休止 / `sui` / `a` / `qu`）一次就出 3 个：
0.600、1.120、1.850 s——正好是每个辅音槽的第一帧（音符起点减去辅音时长）。

### 2.3 根因（三个条件同时成立）

1. bank 缓冲区里"没写过"的帧 MGC 全 0。**MGC[0] 是 log 增益，0 表示幅度 1.0（满幅）**，
   不是静音。
2. 辅音槽写入时用交叉淡化，而 `FadeInWeights(0) = 1 − (1+cos0)/2 = 0`、
   `FadeOutWeights(0) = 1`——**淡化区的第一帧 100% 保留目标缓冲区原值**。前面是休止时，
   原值就是那排 0。
3. `MarkVoiced` 在写之前就把整个辅音槽标成"有声"，静音门不会再压掉它。

于是这一帧以满幅噪声进声码器（BAP 决定它是噪声），再被世界声码器的 2048 点窗摊到
20–30 ms，成为听得到的爆音。

MUTA 的参考音频里没有这种爆音（同一位置 RMS 0.000–0.013），它的休止是真正的安静。插件这边
给"显式休止音符"准备的 sentinel 是 `RestMgcLogGain = −9 dB`，但休止**不是**音符（只是音符
之间的空隙）时缓冲区从来不会被写，才留下满幅的 0。这条是插件侧的构造问题，与 MUTA 的参数化
无关。

### 2.4 建议

- **主修**：bank 缓冲区初始化成 rest sentinel（`c0 = −9`），而不是 0；这样即使踩中第一帧，
  也只是一帧 −9 dB 的极轻声音，不是满幅。
- **同修**：交叉淡化时如果目标帧还没写过，不要在 i=0 保留旧值（先写满幅再淡出，或把
  fadeIn 的第一帧置 1）。
- **兜底**：渲染前把"有声但 `mgc[0]==0`"的帧改回 silence 并记日志（现在是记日志但仍放行）。

## 3. 换气声

### 3.1 MUTA 的实测行为（不一致：我们完全没有）

- 休止中会有一次 **~0.3–0.4 s 的噪声型换气**，位置在下一音符前 **0.2–0.3 s**；
  电平约 **−13 dB**（相对演唱：换气 RMS 0.011，演唱中位 0.048）；
  频谱质心 **4.1 kHz**；**没有 F0**。
- 每次换气的噪声是**独立**的（两段换气原始波形相关 ≈ 0），不是同一段样本重复播放。
- 长休止不一定有：30 s 的空段里没有；2.67 s、3.56 s 的休止里有。
- 频段分布（<500/0.5–2k/2–6k/6–12k/>12k %）：观测 `3.4 / 17.6 / 60.4 / 15.6 / 3.1`。

### 3.2 换气从哪里来

- **不是模型的中文 `sp`**：模型 sp 的参数频段是 `3.3 / 44.8 / 49.2 / 2.1 / 0.5`（明显更暗），
  而且 sp 是 unvoiced，当前链路把"无 F0"一律当静音（`silence[f] = pitch[f] <= 0`），
  模型路径里 sp 根本不会出声。
- **更像 bank 的"尾部 PCM"**：`.inf` 尾部的 20 段 PCM（`InfFile.Final`，float32/48 kHz，
  0.39–0.90 s/段）频段分布是 `4.6 / 21.7 / 54.7 / 16.3 / 2.7`（#19），和观测的换气几乎
  一致；但原始波形相关只有 0.08–0.11，说明不是直接播放，而是被当作噪声源/包络使用
  （或经分析后走参数域）。
- **插件目前把 `InfFile.Final` 解析了却完全没用**——这是现成的、每库自带的数据。
- 日文侧：NIT SONG070 的 `.htsvoice` 里确实有 **`br`** 音素（93 处），但当前 Sinsy 对带
  休止的谱面只生成 `pau`（实测 0 个 `br`）。所以"日文链路 Sinsy 自动换气"在这条实现里
  **没有复现**；模型有能力，标签层没触发。

### 3.3 建议（只做手动，不做自动）

- 新增"换气音符"语义：歌词用 **`br`**（同时接受 `sp`），前端识别为呼吸音，**不参与 bank
  选槽**，不产生声母/韵母；时值 = 音符时值。
- 音源优先级：① 该 bank 的 `.inf` 尾部 PCM（`finals`，随机取一段、按音符时长裁/铺、做
  淡入淡出与包络）；② 没有 finals 的库（weiyang）回退到带通噪声（2–8 kHz），保证功能一致。
- 电平按实测 −13 dB 相对演唱起步，并允许 Energy / Breathiness 轨调制；换气**不接受音高**
  （与 MUTA 一致），音高曲线对它无效。
- 日文：先走同一套 `.inf` finals / 噪声实现，保证中日"手加换气"一致；模型 `br` 这条以后
  再评估（要绕过 Sinsy 的 pau-only 行为，属于另一件事）。
- **不自动插入**：句间休止保持现在的静音（这也是与 MUTA 的有意差异，需在文档里写明）。

### 3.4 已实现（test6）

- 歌词 `br`（同义 `sp`）是换气音符：中文链在标签里放一个 `sp` 停顿（否则前一个韵母会
  铺过它），bank 不选槽；日文链把该音符从 Sinsy 谱面里留空成休止。
- 音源：从 `.inf` finals（`.bnk` 内的尾部 PCM，48 kHz float）随机取一段**连续窗口**；
  库短于音符时才线性拉伸。没有 finals 的库回退到 1.6–8 kHz 带通白噪声。
- 频响：原始 finals 偏暗（质心约 0.9–3.3 kHz），加一道 500 Hz 高通 + 2.5 kHz +6 dB
  高架，实测质心 **2843 Hz**，落在 MUTA 换气实测的 2534–3246 Hz 区间内。
- 电平：每个换气先归一化到 RMS 1，再按**本块演唱 RMS 的 0.224 倍**（−13 dB）混入；
  实测 −12.5 dB。没有演唱帧的块回退到绝对 0.012，避免"单独一个换气"静音。
- 不接受音高：换气音符在 F0 机制里是休止，音高曲线对它无效。宿主可见音素是 `sp`。
- 验收：`breath.cmd`（a / br / a）中换气段 RMS 0.0052、演唱 0.022，−12.5 dB；
  中英两条链都能出声；参考工程没有换气音符，行为不变。

## 4. 音素时长（咬字别扭的来源）

### 4.1 第一次实测：插件公布的音素时长与音符长度不匹配

用 TuneLab 2.1.1 的 `sandbox run` 直接读会话公布的音素（`sandbox.syllable`，就是编辑器
音素带上显示的那份），同一句的速度/音高下：

| 音符 | 音符长 | 声母 leading | 韵母 body | 声母占音符 |
|---|---|---|---|---|
| chu | 250 ms | **ch 170 ms** | u 40 ms | 68% |
| xian | 750 ms | x 180 ms | ian 750 ms | 24% |
| qing | 444 ms | q 175 ms | ing 270 ms | 39% |
| qing | **222 ms** | **q 175 ms** | ing 220 ms | **79%** |
| qu | 667 ms | q 195 ms | v 490 ms | 29% |
| xiang | 222 ms | x 175 ms | iang 220 ms | 79% |
| tian | 667 ms | t 135 ms | ian 665 ms | 20% |

三点异常：

1. **声母时长基本是常数**（q≈175–195、x≈175–180、ch≈170、t≈135），与音符长短无关；
   音符长短只挤压/拉伸韵母。原因是 `LabelBuilder.ApplyConsonantDurations` 给声母标签的
   段长固定成 `MinPhoneDuration(phone)`，模型只按这个固定长度预测，音符长度只体现在韵母
   槽上。
2. **短音符里声母占掉 79–85%**，韵母只剩 40–220 ms；`chu` 250 ms 的音符，韵母只有 40 ms。
3. **公布值与实际发声不是同一份**：`BankRenderer` 把声母再夹到音符的 60%（促音后 30%），
   222 ms 的音符实际只播 ~133 ms 声母，但音素带上写的是 175 ms；`MutaSynthesisSession`
   回传的是**夹之前**的几何。编辑器看到的切分和听到的对不上。

### 4.2 MUTA 的同一处是多少

`qing`（222 ms，116.889 s）逐个 5 ms 帧量两条音频：

| | 声母（高频噪声段） | 韵母起点 | 韵母 |
|---|---|---|---|
| MUTA | −115…−5 ms（**≈110 ms**，RMS 0.005–0.015） | +5 ms | 到下一音符 |
| 插件 | −110…0 ms（≈110–133 ms） | 0 ms | 到下一音符 |

同一声母（q），MUTA 约 **110 ms**，插件公布 **175 ms**、实际播 ~133 ms。MUTA 这个 110 ms
正好接近它自己 `MinPhoneDuration("q")` = 0x122870 ticks = **119 ms**；`ch` 的 110 ms 对应
表里的 111 ms。**这像是 MUTA 用品量表里的定长当声母时长，而插件用的是模型预测的更长值。**

（`x` 表值 142 ms、实测约 110–120 ms，还差一截；这一步需要用更多样本确认，见 4.4。）

### 4.3 结论

- 咬字别扭的主因是**声母时长**：模型给出的声母比 MUTA 用的长 50–80%，短音符上尤其明显；
  而且这份时长既不随音符收放，也不等于实际发声。
- 韵母被挤到很短的音符（`chu` 40 ms）听感就是"字没唱开"。
- 编辑器音素带与音频不一致，会让人误判"这个字应该在这里换"。

### 4.5 已实现（test5）

已按 ③ 的规则落地，改动三处：

1. `LabelBuilder.ConsonantFrames(phone)` / `ConsonantFrames(phone, noteFrames)`：表值换算成帧，
   并按 ③ 取 `min(表值, 音符/2)`；
2. `MutaRenderer` 在几何确定之后、进 bank 之前改写每个声母槽的 `LeadingFrames`（中文且未钉死
   音素的音符），于是 bank 拼接、标签、回传给宿主的 `SynthesizedSyllable` 用的是同一组帧数
   ——"看到的 = 听到的"；
3. `PhoneTimeline` 保留，但只用于对齐/取帧，不再作为时长来源。

同时修掉 §2 的句首爆音：交叉淡化遇到未写帧（`c0 == 0`）直接取源帧；渲染前兜底把"有声但

### 5.1 电平差的归因（test6 实测）

结论：**不是"少加了一个固定增益"，也不是 worldline 连续噪声后端自身掉电平**。

1. 用 `vocoder_level.py` 把同一条 bank 参数（`a/g/sp`、c0 ≈ −5.17）分别送进
   `WorldSynthesis`（WORLD 原始合成）和 `WorldSynthesisContinuousNoise`（插件实际用的后端）：
   RMS **0.07005 vs 0.07003**、峰值 0.486 vs 0.492——连续噪声后端与 WORLD 逐电平一致。
2. 同一段参数在 MUTA 参考音频里对应段的 RMS 更高，且逐帧比值并不恒定：
   p10 **−6.2 dB**、中位 **−2.7 dB**、p90 **+1.2 dB**。固定加 2.7 dB 只会把中位对上，
   动态与音色仍不对。
3. 频谱也不同：在 134.5–134.7 s 的持续音上，MUTA 的基频约比二次谐波低 13 dB，插件基频
   与二次谐波几乎等高；插件在谐波之间还有一组 550–800 Hz 的窄峰（旧构建同样存在）。
   持续音的频段占比：MUTA `[-15.0, -1.1, -7.1, -26.0]` dB，插件 `[-3.2, -3.7, -10.6, -31.7]` dB
   （<0.5k / 0.5–2k / 2–6k / 6–12k）——这是音色/参数域差异，不是增益。

因此剩下的差距来自 **worldline vs MUTA 原声码器（STRAIGHT 系）的合成差异**，以及选槽/
拉伸带来的参数差异；两者用现有证据无法再分开。在没
有这个对照之前，不建议用 `output_gain_db` 或改限幅去"补"这 2.7 dB。

- 参考工程里的连音符和换气都已在 test6 修完（§1.4 / §3.4），电平一项保持原状待定。
